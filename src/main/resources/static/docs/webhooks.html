Webhooks

Have the finished timetable sent to your own system, instead of checking for it.

A webhook is an address on your server that the scheduler sends a message to when something happens, such as a timetable finishing. It's optional. Without one, you can check the status yourself.

Set it up

curl -X PUT $BASE/api/schools/webhook \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "webhookUrl": "https://your-system.example.edu/timetable-hook" }'

The response includes a webhookSecret starting with whsec_.

Save the secret now. It is shown only once. You'll use it to check that messages really come from the scheduler. If you lose it, send "rotateSecret": true to get a new one. The old one stops working immediately.

The address must use https and be reachable from the internet. Private and local addresses are refused.

Test it

curl -X POST $BASE/api/schools/webhook/test -H "Authorization: Bearer $TOKEN"

This sends one WEBHOOK_TEST message and tells you what your server replied.

Change or turn off

  • See current settings: GET /api/schools/webhook
  • Pause deliveries: send "webhookEnabled": false
  • Remove it: send an empty "webhookUrl": ""

What you'll receive

Every message is a POST with a JSON body of the same shape:

{
  "event": "GENERATED_TIMETABLE",
  "deliveryId": "8d0b...",
  "schoolId": "4a1c...",
  "timestamp": "2026-09-09T10:15:00Z",
  "data": { ... }
}
eventSent when
GENERATION_STARTEDThe scheduler has started working on your timetable.
GENERATED_TIMETABLEThe timetable is ready. data.entries holds every class with its day, start and end time, room and lecturer. Check data.feasible.
TIMETABLE_CONFLICTSThe timetable still has clashes, because the scheduler ran out of time.
UNSCHEDULABLE_EVENTSSome classes can't be placed anywhere, usually because of a data problem. More time won't help. See Troubleshooting.
CONFLICT_MAPWhich sections can never share a time slot, and why.
GENERATION_FAILEDNo timetable was produced.
BULK_UPLOAD_RESULTA data upload finished.
WEBHOOK_TESTYou used the test endpoint.

Replying

  • Reply with any 2xx status, such as 200, as soon as you receive the message. Do any slow work afterwards.
  • If your server is down or replies 5xx, the message is sent again up to two more times, after 2 and then 8 seconds.
  • A 4xx reply is not retried.
  • A retried message keeps the same deliveryId. Use it to skip messages you've already handled.

Checking a message is genuine

Each message carries a signature header:

X-Timetable-Signature: t=1757376000,v1=9f86d081884c7d65...

To check it:

  1. Take t and the raw request body, exactly as received, and join them with a dot: t + "." + body.
  2. Compute an HMAC-SHA256 of that string using your webhookSecret as the key, and write it as hex.
  3. Compare it to v1. If they differ, ignore the message.
  4. Also reject messages where t is more than about 5 minutes old.

Example in Node.js

const crypto = require('crypto');

function isGenuine(rawBody, header, secret) {
  const parts = Object.fromEntries(header.split(',').map(p => p.split('=')));
  const expected = crypto.createHmac('sha256', secret)
    .update(parts.t + '.' + rawBody)
    .digest('hex');
  const fresh = Math.abs(Date.now() / 1000 - Number(parts.t)) < 300;
  const given = Buffer.from(parts.v1 || '');
  return fresh && given.length === expected.length
    && crypto.timingSafeEqual(Buffer.from(expected), given);
}

Example in Python

import hmac, hashlib, time

def is_genuine(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    expected = hmac.new(secret.encode(), f"{parts['t']}.".encode() + raw_body,
                        hashlib.sha256).hexdigest()
    fresh = abs(time.time() - int(parts["t"])) < 300
    return fresh and hmac.compare_digest(expected, parts["v1"])

Other headers on every message: X-Timetable-Event, X-Timetable-Delivery, X-Timetable-Attempt and X-Timetable-Timestamp.
